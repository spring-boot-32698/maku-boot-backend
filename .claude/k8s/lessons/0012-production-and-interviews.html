Can maku scale out? Not yet, and here's exactly why

Setting backend.replicaCount: 3 would run, but behave wrongly:

ConcernStatusFix
Login sessions✅ fine: tokens live in Redis, so any replica can serve any user—
DB migrations✅ fine: Liquibase takes a lock in DATABASECHANGELOGLOCK, so one replica migrates and the others wait—
Scheduled jobs❌ Quartz uses an in-memory store, so every replica runs every jobQuartz JDBC store with clustering (the commented-out settings in ScheduleConfig.java, plus QRTZ_* tables via a Liquibase changeset)
Uploaded files❌ RWO volume, one node only; each replica would see different filesObject storage, which maku already supports (storage.config.type: minio|aliyun|tencent|…), or an RWX volume
Deploy strategy⚠️ Recreate (downtime per deploy) because of the RWO volumeOnce uploads are off the volume, switch to RollingUpdate

That analysis (what state lives where) is exactly what interviewers mean by “is this app cloud-native?”. The frontend has no such state, so it can scale freely today.

Hands-on: watch an autoscaler work

A HorizontalPodAutoscaler adjusts replicas to hit a target metric. It computes CPU % relative to requests, which is why requests matter (lesson 06). It reads metrics from metrics-server, which k3s ships.

  1. An app with CPU requests, a Service, and an autoscaler targeting 50% CPU, between 1 and 5 replicas.

    kubectl create namespace play
kubectl -n play create deployment web --image=nginx:1.27-alpine
kubectl -n play set resources deploy/web --requests=cpu=20m --limits=cpu=100m
kubectl -n play expose deploy web --port=80
kubectl -n play autoscale deploy/web --cpu-percent=50 --min=1 --max=5

  2. Generate load from inside the cluster, and watch. (Metrics take ~30 s to appear; until then TARGETS shows <unknown>.)

    kubectl -n play run load --image=busybox:1.36 --restart=Never -- sh -c 'while true; do wget -q -O /dev/null http://web; done'
kubectl -n play get hpa web -w
    What happened when I ran it
    NAME   REFERENCE        TARGETS              MINPODS   MAXPODS   REPLICAS
web    Deployment/web   cpu: <unknown>/50%   1         5         1
web    Deployment/web   cpu: 500%/50%        1         5         1      ← ~40 s in; desired replicas → 4
web    Deployment/web   cpu: …               1         5         4

  3. Stop the load and watch it scale back down. Scale-down waits about 5 minutes by default (a stabilisation window), so it doesn't flap. Then clean up.

    kubectl -n play delete pod load
kubectl -n play get hpa web -w      # Ctrl-C when bored
kubectl delete namespace play

Practice

1. Why can't maku just run backend.replicaCount: 3 today?

Sessions are in Redis and Liquibase locks, so both are fine. The in-memory Quartz store and the RWO uploads volume are the real blockers. The backend is a Deployment, not a StatefulSet.

2. The HPA shows cpu: <unknown>/50% forever. Most likely cause?

Utilisation is usage ÷ request. With no request there's nothing to divide by, and without metrics-server there's no usage. (It's also normal for the first ~30 s.)

3. What is “GitOps”, as Argo CD and Flux practise it?

Desired state lives in git; an in-cluster agent pulls and reconciles it continuously. That's the same reconcile idea as lesson 01, applied to deployments. Rollback = git revert.

4. What does a PodDisruptionBudget protect against?

During node drains and upgrades, a PDB (e.g. minAvailable: 1) makes the eviction wait. It needs ≥ 2 replicas to be meaningful. Memory → limits; network → NetworkPolicy; accidents → RBAC.

5. Your company's cluster pulls from a private registry. What does the pod spec need?

A kubernetes.io/dockerconfigjson Secret referenced from the pod (or its ServiceAccount). Without it you get ImagePullBackOff with “unauthorized” (lesson 11, lab B's cousin).
