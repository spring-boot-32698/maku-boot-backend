ConfigMaps and Secrets

Same image everywhere; the environment tells it where it is.

Time ~12 minPrereq Lesson 03Run from maku-boot-backend/
Your win

You can trace any Spring setting from values.yaml to the running JVM, change one safely with Helm, and explain what a Secret does and doesn't protect.

From values to the JVM

values-k3d.yaml        backend.publicUrl: http://api.maku.localhost:8088
   │  helm renders templates/backend-configmap.yaml
   ▼
ConfigMap maku-backend STORAGE_CONFIG_DOMAIN: http://api.maku.localhost:8088
   │  Deployment:  envFrom: - configMapRef: maku-backend
   ▼
container env          STORAGE_CONFIG_DOMAIN=http://api.maku.localhost:8088
   │  Spring relaxed binding: UPPER_SNAKE → lower.dotted
   ▼
Spring property        storage.config.domain   (overrides application.yml)

A ConfigMap holds plain settings; a Secret holds sensitive ones. The DB password comes in through a single env entry with valueFrom.secretKeyRef → Secret maku-db, key mysql-password. MySQL's StatefulSet reads the same Secret, so app and database always agree.

Compose equivalent: environment:. Spring's mapping rules: Spring Boot cloud deployment and the “relaxed binding” section of the Spring Boot reference.

Two facts that bite people

  1. Secrets are base64, not encryption. Anyone allowed to get secrets in the namespace can read them. Protection comes from RBAC, encryption-at-rest of etcd, and keeping the values out of git. That's why the chart has database.existingSecret for real environments. Secret docs say this in a warning box near the top.
  2. Env vars are read once, at container start. Editing a ConfigMap does nothing to running pods. Our chart therefore puts a checksum/config annotation (a hash of the rendered ConfigMap) on the pod template. Change the config → the hash changes → the template changes → the Deployment rolls new pods.

Hands-on

  1. Read the ConfigMap Helm generated.

    kubectl -n maku get configmap maku-backend -o yaml

  2. Read the “secret” password. One command is all it takes.

    kubectl -n maku get secret maku-db -o yaml
kubectl -n maku get secret maku-db -o jsonpath='{.data.mysql-password}' | base64 -d; echo
    Expected output
    maku123456

  3. See what the JVM actually received.

    kubectl -n maku exec deploy/maku-backend -c backend -- env | grep -E '^(SPRING_|STORAGE_|TZ)' | sort
    Expected output
    SPRING_DATASOURCE_DYNAMIC_DATASOURCE_MASTER_PASSWORD=maku123456   ← from the Secret
SPRING_DATASOURCE_DYNAMIC_DATASOURCE_MASTER_URL=jdbc:mysql://maku-mysql:3306/maku_boot?…
SPRING_DATA_REDIS_HOST=maku-redis
SPRING_PROFILES_ACTIVE=dev
STORAGE_CONFIG_DOMAIN=http://api.maku.localhost:8088
TZ=Asia/Shanghai                                                   ← why log times differ from your clock

  4. Change a setting the right way: turn on debug logging for net.maku through Helm, and watch the rollout in a second terminal (kubectl -n maku get pods -w).

    helm upgrade maku deploy/helm/maku -n maku -f deploy/helm/maku/values-k3d.yaml \
  --set 'backend.extraEnv[0].name=LOGGING_LEVEL_NET_MAKU' \
  --set 'backend.extraEnv[0].value=debug' --wait
    What to notice

    The old backend pod terminates first (Recreate), a new one starts, and its logs (kubectl -n maku logs deploy/maku-backend | grep DEBUG | head) now show DEBUG lines. helm history maku -n maku has a new revision.

  5. Put it back. Running the same upgrade without the --set flags removes the extra env.

    helm upgrade maku deploy/helm/maku -n maku -f deploy/helm/maku/values-k3d.yaml --wait
helm get values maku -n maku
Why not kubectl edit configmap?It works for a quick test, but the change lives only in the cluster: the next helm upgrade overwrites it, and nobody can see it in git. Treat the chart and values files as the source of truth.

Practice

1. kubectl get secret maku-db -o yaml shows the password how?

You decoded it with base64 -d in step 2. Encoding is not encryption.

2. The env var SPRING_DATA_REDIS_HOST sets which Spring property?

Relaxed binding: lowercase, underscores become dots. That's why the chart can configure Spring entirely through env vars without touching application.yml.

3. Someone edits the ConfigMap by hand. The running backend…

Env vars are fixed at container start. (ConfigMaps mounted as files do update eventually, but the app must re-read them.) Helm's checksum annotation is what triggers restarts in our chart.

4. Why is the DB password in a Secret but the DB URL in a ConfigMap?

RBAC can allow reading ConfigMaps but not Secrets; Secrets aren't printed by describe; tools such as External Secrets and Sealed Secrets plug in there. But they aren't encrypted by default (question 1).

5. What does the checksum/config annotation on the backend pod template achieve?

Any template change creates a new ReplicaSet (lesson 02). Hashing the ConfigMap into an annotation links “config changed” to “pods restart”.
Recall: list three ways to give a container configuration in Kubernetes.

(1) env with literal values or valueFrom (configMapKeyRef / secretKeyRef / fieldRef); (2) envFrom a whole ConfigMap or Secret; (3) mount a ConfigMap/Secret as a volume (files), which updates in place over time. Plus command-line args, as MySQL uses for its charset.
