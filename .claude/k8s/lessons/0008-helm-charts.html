Helm charts from the inside

A chart is a folder of YAML with blanks in it. Values fill the blanks.

Time ~18 minPrereq lessons 01–07Run from maku-boot-backend/
Your win

You can read any template in deploy/helm/maku, predict what it renders, and add a new configurable feature to the chart.

What Helm adds over plain YAML

  • Parameters: one chart, many environments (values-k3d.yaml vs values-production.example.yaml).
  • A release: everything installed together is tracked as one unit with numbered revisions, so you can upgrade, roll back, or uninstall it as a whole.
  • Packaging: charts can be versioned, shared, and depended on (helm install bitnami/…).

Helm 4 (your version) renders charts the same way as Helm 3. apiVersion: v2 charts “continue to work unchanged” (Helm 4 overview). New installs use server-side apply.

Anatomy of deploy/helm/maku

Chart.yaml          name, version (the chart's), appVersion (the app's, = default image tag)
values.yaml         every knob with its default
values-k3d.yaml     overrides for the local cluster
templates/
  _helpers.tpl      named snippets: maku.fullname, maku.labels, maku.selectorLabels, maku.image …
  *.yaml            one or more manifests each, with {{ template actions }}
  NOTES.txt         printed after install/upgrade
  tests/            helm test hooks

The template language in ten patterns

Helm uses Go templates plus the Sprig function library. Everything below appears in our chart:

PatternMeaning
{{ .Values.backend.service.port }}read a value
{{ .Release.Name }}, .Release.Namespace, .Chart.AppVersionbuilt-in objects
{{ .Values.x | quote }}pipeline: pass the value into a function
{{ default .Chart.AppVersion .image.tag }}fallback if empty
{{ required "msg" .Values.externalDatabase.host }}fail rendering with a helpful message
{{- if .Values.mysql.enabled }} … {{- end }}conditional block (the - trims whitespace)
{{- with .Values.backend.extraEnv }} {{- toYaml . | nindent 12 }} {{- end }}only if non-empty; . becomes that value; dump as YAML indented 12
{{ include "maku.labels" . | nindent 4 }}call a named template from _helpers.tpl, then indent it
{{ include "maku.selectorLabels" (dict "ctx" . "component" "backend") }}pass several arguments by building a dict
{{ include (print $.Template.BasePath "/backend-configmap.yaml") . | sha256sum }}render another template and hash it (the checksum/config trick)

Sources: Chart Template Guide → functions and pipelines, control structures, named templates.

Value precedence: values.yaml < -f first.yaml < -f second.yaml < --set. Later wins. docs

Helm renders textTemplates produce text that only has to look like YAML. helm lint and helm template won't notice replicas: two. In my tests, not even helm upgrade --dry-run=server caught it. The Kubernetes API server is what validates types. The kubectl apply --dry-run=server in step 5 asks it directly.

Hands-on

  1. Render one template with a different value. Nothing touches the cluster.

    helm template maku deploy/helm/maku --show-only templates/backend-configmap.yaml --set backend.springProfile=prod
    What to notice

    SPRING_PROFILES_ACTIVE: "prod", and every name starts with maku- (from the release name).

  2. How names are built: render with a different release name and read maku.fullname in _helpers.tpl.

    helm template foo deploy/helm/maku --show-only templates/backend-service.yaml | grep -E 'name:|instance'
    Expected output
      name: foo-maku-backend          ← release "foo" doesn't contain "maku", so: <release>-<chart>
    app.kubernetes.io/instance: foo

    With release maku the name is just maku-backend: fullname avoids maku-maku-backend.

  3. Trip a required guard on purpose.

    helm template maku deploy/helm/maku --set mysql.enabled=false
    Expected output
    Error: execution error at (maku/templates/backend-deployment.yaml:24:28): externalDatabase.host is required when mysql.enabled=false

  4. Inspect the live release: the values you supplied vs everything computed, and the manifests actually applied.

    helm get values maku -n maku
helm get values maku -n maku --all | head -20
helm get manifest maku -n maku | grep -E '^kind:' | sort | uniq -c

  5. See what Helm misses: a wrongly typed value sails through, and the API server catches it.

    helm lint deploy/helm/maku --set backend.replicaCount=two
helm template dryrun deploy/helm/maku --set backend.replicaCount=two --show-only templates/backend-deployment.yaml \
  | kubectl apply --dry-run=server -n maku -f -
    Expected output
    1 chart(s) linted, 0 chart(s) failed
Error from server (BadRequest): … cannot unmarshal string into Go struct field DeploymentSpec.spec.replicas of type int32

  6. Your turn: add a feature. Make extra pod annotations configurable (teams use them for Prometheus scraping and similar). Work on a copy so the real chart stays clean:

    cp -r deploy/helm/maku /tmp/maku-chart

    Goal: --set-string 'backend.podAnnotations.prometheus\.io/scrape=true' should add that annotation next to checksum/config in the backend pod template, and with no value set, nothing should change. Edit /tmp/maku-chart/values.yaml and templates/backend-deployment.yaml, then check:

    helm lint /tmp/maku-chart
helm template maku /tmp/maku-chart --set-string 'backend.podAnnotations.prometheus\.io/scrape=true' \
  --show-only templates/backend-deployment.yaml | sed -n '/template:/,/spec:/p'
    Solution (try first!)
    # values.yaml, under backend:
  podAnnotations: {}

# templates/backend-deployment.yaml, right after the checksum/config line:
        {{- with .Values.backend.podAnnotations }}
        {{- toYaml . | nindent 8 }}
        {{- end }}

# rendered:
      annotations:
        checksum/config: f53a0ed4…
        prometheus.io/scrape: "true"

Practice

1. values.yaml says springProfile: dev, -f prod.yaml says prod, and --set backend.springProfile=test is passed. Result?

Defaults < files (in order) < --set. The most specific, last source wins.

2. Why does the chart write include "maku.labels" . | nindent 4 instead of plain template "maku.labels" .?

template writes output directly and can't be piped. YAML is indentation-sensitive, so you almost always need include … | nindent N (newline + indent N).

3. maku.selectorLabels leaves out app.kubernetes.io/version and helm.sh/chart. Why?

A Deployment's spec.selector can't be changed after creation. If it included the version, the next upgrade would fail. Stable identity goes in selectors; everything else goes in maku.labels.

4. You install the chart with release name shop. What is the backend Service called?

maku.fullname = release name if it already contains the chart name, else <release>-<chart>. fullnameOverride replaces it entirely.

5. Which check would catch replicas: two before it reaches a real cluster?

Only the API server knows the schemas (offline tools like kubeconform also work). Helm checks template syntax and chart structure, not Kubernetes types.
Recall (interview): “Why use Helm instead of plain YAML or Kustomize?”

Helm gives parameterised templates, a release abstraction with revisions (upgrade/rollback/uninstall as a unit), hooks (tests, migrations), and packaging/sharing via repositories. Plain YAML has none of that; Kustomize patches plain YAML without templating and is built into kubectl. Teams often pick Kustomize for in-house apps and Helm for distributing software, or combine them (Helm render + Kustomize patch). Downsides of Helm: templated YAML is harder to read, and errors appear late.
