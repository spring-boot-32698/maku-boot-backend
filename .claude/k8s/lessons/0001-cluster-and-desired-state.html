The cluster and desired state

Docker Compose does what you say, once. Kubernetes keeps making it true, forever.

Time ~12 minPrereq Docker ComposeCluster k3d-maku
Your win

You can name the parts of a cluster, point at them on your own machine, and explain why a pod you delete comes back.

From “run this” to “keep this true”

With Compose, docker compose up starts containers on one machine and then walks away. Kubernetes works differently: you store a description of what you want — “one backend pod, one MySQL with 5 GiB of disk” — and controllers keep comparing that desired state with what's actually running, fixing any difference. Every object you create has a spec (what you want) and a status (what is).

Kubernetes docs: Objects in Kubernetes — the “spec and status” section is the core idea of the whole system.

Who does what

PartJob
Control plane (the brain)
kube-apiserverThe only front door. kubectl, controllers and nodes all talk to it.
etcdDatabase holding every object.
kube-schedulerPicks a node for each new pod.
kube-controller-managerRuns the reconcile loops (Deployments, ReplicaSets, …).
Every node (the muscle)
kubeletStarts the pods assigned to its node, runs their probes, reports status.
container runtimecontainerd — actually runs containers.
kube-proxyMakes Service IPs route to pods (lesson 03).

Source: Kubernetes Components. k3s packs all of these into one binary; k3d runs k3s inside Docker containers.

On your machine, k3d fakes the machines: each node is a Docker container running k3s. Our cluster (deploy/k3d/cluster.yaml) has one server (control plane, can also run pods) and one agent (worker).

Hands-on: look around

  1. Which cluster is kubectl pointed at? (You also have an old k3d-ecommerce context — always check.)

    kubectl config current-context
    Expected output
    k3d-maku

  2. The nodes, as Kubernetes sees them…

    kubectl get nodes
    Expected output
    NAME                STATUS   ROLES                  AGE   VERSION
k3d-maku-agent-0    Ready    <none>                 7m    v1.31.5+k3s1
k3d-maku-server-0   Ready    control-plane,master   7m    v1.31.5+k3s1

  3. …and as Docker sees them. Same names: the “machines” are containers. (The extra serverlb is k3d's load balancer that owns port 8088.)

    docker ps --filter name=k3d-maku --format '{{.Names}}\t{{.Ports}}'

  4. Every pod in every namespace. kube-system holds the cluster's own add-ons; maku holds our app.

    kubectl get pods -A
    Expected output
    NAMESPACE     NAME                                      READY   STATUS      RESTARTS
kube-system   coredns-ccb96694c-s7msh                   1/1     Running     0     ← cluster DNS (lesson 03)
kube-system   helm-install-traefik-vg7pf                0/1     Completed   1     ← k3s installs Traefik with Helm!
kube-system   local-path-provisioner-5cf85fd84d-bvv2k   1/1     Running     0     ← creates disks (lesson 05)
kube-system   metrics-server-5985cbc9d7-gjj49           1/1     Running     0     ← powers `kubectl top`
kube-system   traefik-5d45fc8cc9-snmw5                  1/1     Running     0     ← ingress controller (lesson 07)
maku          maku-backend-779d8657fd-pvnnc             1/1     Running     0
maku          maku-frontend-594dc88588-94dmm            1/1     Running     0
maku          maku-mysql-0                              1/1     Running     0
maku          maku-redis-5897945945-65md4               1/1     Running     0

  5. Which node did the scheduler pick for each maku pod?

    kubectl -n maku get pods -o wide
    What to notice

    The NODE column: pods are spread across k3d-maku-server-0 and k3d-maku-agent-0. You never chose — the scheduler did.

  6. Desired state in action. Open a second terminal and watch; then delete the frontend pod in the first.

    kubectl -n maku get pods -w
    kubectl -n maku delete pod -l app.kubernetes.io/component=frontend
    What to notice

    The old pod goes Terminating and, within a second, a new pod with a different name appears and becomes Running. Nobody restarted it: a controller saw “want 1, have 0” and created a replacement. http://maku.localhost:8088 keeps working.

  7. Peek at spec vs status of that new pod (scroll: spec: near the top, status: at the bottom).

    kubectl -n maku get pod -l app.kubernetes.io/component=frontend -o yaml | less

Practice

Answer from memory.

1. You run kubectl apply. Which component does kubectl actually talk to?

Everything goes through kube-apiserver; it validates the object and stores it in etcd. The scheduler and kubelets then react to what's stored.

2. Who decides which node a new pod runs on?

The scheduler assigns a node; then that node's kubelet starts the pod through the container runtime.

3. You deleted the frontend pod and a new one appeared. Why?

The pod belongs to a ReplicaSet (owned by the Deployment) whose spec says replicas: 1. The ReplicaSet controller saw 0 and created one — a new pod, hence the new name. Helm only acts when you run it.

4. In our k3d setup, what is a “node”?

docker ps showed k3d-maku-server-0 and k3d-maku-agent-0. In production a node is usually a VM or physical machine; Kubernetes doesn't care which.

5. In an object's YAML, which part do you write and which does Kubernetes fill in?

spec = desired state (yours, usually via Helm). status = observed state, written by controllers and kubelets.
Recall (interview classic): “What happens when you run kubectl create deployment?” Answer out loud, then open.

kubectl sends the Deployment to the API server → stored in etcd → the Deployment controller creates a ReplicaSet → the ReplicaSet controller creates Pod objects → the scheduler assigns each pod a node → that node's kubelet sees it, pulls the image via the container runtime, starts it, and reports status back to the API server.
