Storage and StatefulSets

Pods are cattle. Their data shouldn't be.

Time ~15 minPrereq Lesson 04Namespace maku
Your win

You can prove that MySQL's data survives its pod being deleted, explain why Redis's doesn't, and read a StorageClass to predict how volumes behave.

Three objects

Pod maku-mysql-0 ── mounts ──► PVC data-maku-mysql-0   "I need 5Gi, ReadWriteOnce"     (namespaced, yours)
                                   │ bound to
                                   ▼
                               PV pvc-9dd1…            the actual disk                  (cluster-wide)
                                   ▲ created on demand by
                               StorageClass local-path  "how to make disks": a directory on the node
  • PVC = a request, PV = the storage, StorageClass = the recipe. With dynamic provisioning you only write the PVC. docs
  • k3s's local-path class makes a folder on whichever node the pod first lands on (WaitForFirstConsumer). From then on, the volume — and so the pod — is tied to that node.
  • Access modes: RWO (one node at a time) is what most disks offer; RWX (many nodes) needs network storage such as NFS or CephFS.
  • Reclaim policy Delete: deleting the PVC deletes the PV and the data.

Compose equivalent: the named volume mysql-data:. Kubernetes splits that into request (PVC) and supply (PV/StorageClass) so the same chart works on any infrastructure.

Why MySQL is a StatefulSet

A Deployment's pods are interchangeable: random names, and if they share one PVC they share one disk. A StatefulSet gives each replica:

  • a stable name: maku-mysql-0, always, even after deletion;
  • its own PVC from volumeClaimTemplates: data-maku-mysql-0 (then -1, -2…), re-attached to the same-named pod;
  • ordered start/stop, plus a stable DNS name through the headless Service (maku-mysql-0.maku-mysql-headless).

It does not make MySQL highly available. Replication and failover are MySQL's job (or an operator's). Our StatefulSet runs one instance.

Source: StatefulSets. Note: PVCs created from volumeClaimTemplates are kept when the StatefulSet is deleted (default retention policy).

Hands-on

  1. The claims, the volumes behind them, and the recipe.

    kubectl -n maku get pvc
kubectl get pv
kubectl get storageclass
    Expected output (trimmed)
    NAME                STATUS   CAPACITY   ACCESS MODES   STORAGECLASS
data-maku-mysql-0   Bound    5Gi        RWO            local-path
maku-uploads        Bound    2Gi        RWO            local-path

NAME                   PROVISIONER             RECLAIMPOLICY   VOLUMEBINDINGMODE
local-path (default)   rancher.io/local-path   Delete          WaitForFirstConsumer

  2. Which node holds MySQL's disk?

    kubectl -n maku get pod maku-mysql-0 -o wide
    What to notice

    On the reference run it's k3d-maku-server-0. Delete the pod as often as you like: it always comes back on that node, because its local-path volume lives there.

  3. Write something to MySQL.

    kubectl -n maku exec maku-mysql-0 -- sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" maku_boot -e \
  "create table if not exists k8s_lesson(t datetime); insert into k8s_lesson values(now()); select * from k8s_lesson"'

  4. Predict: will the row survive? Then delete the pod and wait for its replacement.

    kubectl -n maku delete pod maku-mysql-0
kubectl -n maku wait --for=condition=ready pod/maku-mysql-0 --timeout=180s
kubectl -n maku exec maku-mysql-0 -- sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" maku_boot -e "select * from k8s_lesson"'
    What happens

    Same pod name, same row. The PVC data-maku-mysql-0 was re-attached. While MySQL was down, the backend's readiness (which includes db) failed briefly; check kubectl -n maku get pods.

  5. Now Redis, which has no volume. Write a key, kill the pod, look again.

    kubectl -n maku exec deploy/maku-redis -- redis-cli -n 1 set lesson hello
kubectl -n maku delete pod -l app.kubernetes.io/component=redis
kubectl -n maku rollout status deploy/maku-redis
kubectl -n maku exec deploy/maku-redis -- redis-cli -n 1 get lesson
    What happens

    An empty line (interactive redis-cli would say (nil)): the data died with the container. Since login tokens live in Redis (sys:token:*), everyone logged into http://maku.localhost:8088 is now logged out. Try it.

  6. Clean up the lesson table.

    kubectl -n maku exec maku-mysql-0 -- sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" maku_boot -e "drop table k8s_lesson"'
Uninstall ≠ delete datahelm uninstall maku removes the StatefulSet but keeps data-maku-mysql-0 (StatefulSet PVC retention) and maku-uploads (helm.sh/resource-policy: keep). Reinstalling picks the old data back up. To really wipe: kubectl -n maku delete pvc --all.

Practice

1. The MySQL pod is deleted and recreated. Why is the data still there?

The pod is disposable; the claim data-maku-mysql-0 isn't. The StatefulSet mounts the same claim into the new maku-mysql-0.

2. What does a StatefulSet give MySQL that a Deployment wouldn't?

Identity and per-replica storage. Backups and failover are still your job (or a database operator's).

3. Access mode ReadWriteOnce means the volume is…

“Once” = one node. Several pods on the same node can share an RWO volume; pods on different nodes can't. That's why maku-backend uses Recreate (lesson 02).

4. The Redis pod is deleted. What do users notice?

Redis has no PVC in our chart, a deliberate choice since it holds only sessions, caches and a log queue. Files are on maku-uploads; rows are in MySQL.

5. You helm uninstall maku, then install again. The old users are still there. Why?

Default persistentVolumeClaimRetentionPolicy is Retain. The new StatefulSet finds data-maku-mysql-0 by name and mounts it, and Liquibase sees its changesets already applied.
Recall (interview): “Deployment vs StatefulSet — when would you use each?”

Deployment: stateless, interchangeable replicas (APIs, web frontends; maku-backend, maku-frontend). Random names, shared template, rolling updates. StatefulSet: each replica needs a stable identity and its own persistent storage (databases, Kafka, ZooKeeper; maku-mysql). Stable names and DNS, per-replica PVCs, ordered rollout. Many teams avoid running databases in-cluster at all and use managed services instead (see values-production.example.yaml).
