Ship a change, then roll it back

Deploying is easy. Deploying safely means knowing exactly how you'll undo it.

Time ~20 minPrereq Lesson 09Run from maku-boot-backend/
Your win

You ship a real code change as a new image version, survive a broken release without downtime, and roll back on purpose.

The release loop

change code → build image with a NEW tag → make it available to the cluster → helm upgrade --set …tag=NEW
                                                                         ↓ watch / verify
                                                     helm history · helm rollback <revision>
  • Always a new tag. Re-using 5.0.0 for different code means Kubernetes sees no change in the pod template, so no rollout, and nodes may keep the old cached image. Tags should be immutable; real pipelines use the version or the git SHA.
  • Rollback = redeploy an old revision's manifests. helm rollback maku 5 creates a new revision whose content equals revision 5. History only grows.
  • Helm 4 flags. --rollback-on-failure (Helm 3 called it --atomic) waits for readiness and automatically rolls back if the upgrade fails. --force is now --force-replace (Helm 4 overview).

Strategy decides whether a broken release hurts

maku-frontend (RollingUpdate)maku-backend (Recreate)
New version can't startOld pod keeps serving; the new one waits in ImagePullBackOff. Users notice nothing.Old pod was already stopped. Users get errors until you fix or roll back.

That's the real cost of the Recreate trade-off from lesson 02. It's why lesson 12 lists what maku needs to run more than one backend replica.

Hands-on

  1. Note where you start.

    helm history maku -n maku
kubectl -n maku get deploy maku-frontend -o jsonpath='{.spec.template.spec.containers[0].image}'; echo

  2. Make a visible code change: the login page title.

    sed -i "s/title: 'MAKU Low Code'/title: 'MAKU on Kubernetes'/" ../maku-admin-frontend/src/i18n/lang/en-US.ts
git -C ../maku-admin-frontend diff --stat

  3. Build it as 5.0.1 and give it to the cluster.

    docker build -t maku-admin:5.0.1 --build-arg VITE_API_URL=http://api.maku.localhost:8088 ../maku-admin-frontend
k3d image import maku-admin:5.0.1 -c maku

  4. Ship it, watching pods in a second terminal. Then hard-refresh the login page.

    helm upgrade maku deploy/helm/maku -n maku -f deploy/helm/maku/values-k3d.yaml \
  --set frontend.image.tag=5.0.1 --wait
helm history maku -n maku | tail -2
    What to notice

    A new frontend pod starts, becomes ready, and only then the old one terminates (RollingUpdate). The title reads “MAKU on Kubernetes”. History has a new deployed revision; the previous one is superseded.

  5. Ship a broken release (a typo'd tag), with automatic rollback. While it hangs, keep reloading the site.

    helm upgrade maku deploy/helm/maku -n maku -f deploy/helm/maku/values-k3d.yaml \
  --set frontend.image.tag=5.0.2 --rollback-on-failure --timeout 90s
    What happened when I ran it
    Error: UPGRADE FAILED: release maku failed, and has been rolled back due to rollback-on-failure being set:
resource Deployment/maku/maku-frontend not ready. status: InProgress … context deadline exceeded

$ helm history maku -n maku | tail -3
6   superseded   Upgrade complete
7   failed       Upgrade "maku" failed: resource Deployment/maku/maku-frontend not ready …
8   deployed     Rollback to 6

    The site never went down: the 5.0.1 pod kept serving while the 5.0.2 pod sat in ImagePullBackOff.

  6. Now roll back by choice to the revision that ran 5.0.0 (find its number in history).

    helm history maku -n maku
helm rollback maku <revision-with-5.0.0> -n maku --wait
kubectl -n maku get deploy maku-frontend -o jsonpath='{.spec.template.spec.containers[0].image}'; echo
    Expected output
    Rollback was a success! Happy Helming!
maku-admin:5.0.0

    The title is back to “MAKU Low Code” after a hard refresh.

  7. The trap: --set isn't remembered between upgrades. Run a “harmless” upgrade without it, and the image tag falls back to the default (appVersion). That's why teams keep tags in a values file or have CI pass them every time.

    helm get values maku -n maku     # no frontend.image.tag here
helm upgrade maku deploy/helm/maku -n maku -f deploy/helm/maku/values-k3d.yaml --wait   # would reset any --set tag

  8. Undo the code change.

    git -C ../maku-admin-frontend checkout src/i18n/lang/en-US.ts

Practice

1. You fixed a bug, rebuilt as maku-boot:5.0.0 (same tag), imported it, and ran helm upgrade. Nothing changes. Why?

The Deployment spec is byte-for-byte identical, so no new ReplicaSet is created. (kubectl rollout restart would force new pods.) Use a new tag every build.

2. helm rollback maku 5 while at revision 8. What is the current revision afterwards?

Rollbacks are recorded as new revisions (“Rollback to 5”), so history is an audit log you can always roll forward from.

3. A bad frontend tag was deployed. Why did users see no outage?

With RollingUpdate, old pods are removed only as new ones become ready. Helm doesn't check images exist; the kubelet discovers it at pull time.

4. The same bad tag on maku-backend (Recreate). What happens?

Recreate scales the old ReplicaSet to 0 before creating new pods. --rollback-on-failure limits the damage to the timeout window.

5. What is the Helm 4 name for Helm 3's --atomic?

From the Helm 4 overview: --atomic → --rollback-on-failure, --force → --force-replace. The old names still work, with a deprecation warning. Expect both in job adverts and older scripts.
Recall (interview): “A deploy went bad in production. What do you do?”

Stabilise first: helm rollback <release> <last-good> (or kubectl rollout undo), and confirm health. Then investigate: helm history, kubectl describe/logs --previous on the failed pods, diff the values (helm get values --revision N). Prevent: readiness probes plus RollingUpdate (so bad pods never get traffic), --rollback-on-failure in CI, immutable tags, and progressive delivery (canary) for risky changes.
