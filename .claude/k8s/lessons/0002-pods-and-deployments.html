Pods, ReplicaSets, Deployments

You almost never create a pod. You create a Deployment and let it manage pods for you.

Time ~15 minPrereq Lesson 01Namespace play
Your win

You can deploy, scale, update and roll back an app with kubectl — and read maku-backend's Deployment line by line.

Three layers

Deployment  maku-backend               "run this pod template, 1 replica, update by Recreate"
  └─ ReplicaSet  maku-backend-779d8657fd   "keep exactly 1 pod matching these labels"   (hash = template version)
       └─ Pod  maku-backend-779d8657fd-pvnnc   one or more containers sharing an IP
  • A Pod is disposable. If it dies, it's replaced with a new one (new name, new IP), never repaired.
  • A ReplicaSet keeps N pods alive. It finds “its” pods by label selector.
  • A Deployment manages ReplicaSets. Change the pod template (image, env…) and it creates a new ReplicaSet, shifting pods from old to new. That's a rollout, and the old ReplicaSet is kept for rollback.

Compose equivalent: one services: entry ≈ Deployment + pod template. Source: Deployments.

Two update strategies

RollingUpdate (default): start new pods, wait until they're ready, then stop old ones, so there's no downtime. Recreate: stop all old pods, then start new ones, with a brief gap. maku-backend uses Recreate because its uploads volume is ReadWriteOnce: if the new pod were scheduled on the other node while the old pod still held the volume, it couldn't mount it (lesson 05).

Hands-on

  1. Make a scratch namespace so you can't hurt maku.

    kubectl create namespace play

  2. Create a Deployment of nginx with 2 replicas, then look at all three layers with their labels.

    kubectl -n play create deployment web --image=nginx:1.27-alpine --replicas=2
kubectl -n play get deploy,rs,pods --show-labels
    Expected output (hashes differ)
    NAME                  READY   UP-TO-DATE   AVAILABLE   LABELS
deployment.apps/web   2/2     2            2           app=web
NAME                             DESIRED   CURRENT   READY   LABELS
replicaset.apps/web-5d8f7c9b6d   2         2         2       app=web,pod-template-hash=5d8f7c9b6d
NAME                       READY   STATUS    LABELS
pod/web-5d8f7c9b6d-4kq2x   1/1     Running   app=web,pod-template-hash=5d8f7c9b6d
pod/web-5d8f7c9b6d-x8m9z   1/1     Running   app=web,pod-template-hash=5d8f7c9b6d

  3. Predict, then do: remove the app=web label from one pod. What will the ReplicaSet do?

    kubectl -n play label pod <one-pod-name> app-
kubectl -n play get pods --show-labels
    What happens

    You now see 3 pods. The unlabelled one no longer matches the selector, so it's an orphan the ReplicaSet ignores; it created a new pod to get back to 2. Selection is purely by labels. Clean up the orphan: kubectl -n play delete pod <that-pod>.

  4. Scale up, and watch the scheduler spread pods across nodes.

    kubectl -n play scale deploy/web --replicas=4
kubectl -n play get pods -o wide

  5. Roll out a new version. A second terminal with kubectl -n play get rs -w shows the hand-over.

    kubectl -n play set image deploy/web nginx=nginx:1.28-alpine
kubectl -n play rollout status deploy/web
kubectl -n play get rs
    What to notice
    NAME             DESIRED   CURRENT   READY
web-5d8f7c9b6d   0         0         0      ← old version, kept for rollback
web-7b9c6d8f4c   4         4         4      ← new version

  6. Simulate “the new version is broken”: roll back.

    kubectl -n play rollout history deploy/web
kubectl -n play rollout undo deploy/web
kubectl -n play get deploy web -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
    Expected output
    nginx:1.27-alpine

  7. Now read the real thing. Find replicas, strategy, selector.matchLabels, the template's labels, initContainers, image, and the three *Probe blocks.

    kubectl -n maku get deploy maku-backend -o yaml | less

    Compare with the source template: deploy/helm/maku/templates/backend-deployment.yaml.

Practice

1. What is the smallest deployable unit in Kubernetes?

Kubernetes schedules pods, not containers. A pod can hold several containers (plus init containers, like maku-backend's wait-for-mysql) that share one IP.

2. How does a ReplicaSet know which pods are its own?

You proved it in step 3: removing a label orphaned the pod. Names are cosmetic; a namespace can hold many apps.

3. You change a Deployment's image (default strategy). What happens?

RollingUpdate replaces pods gradually; the old ReplicaSet stays at 0 replicas for rollout undo. “All stop, then start” is Recreate. Containers are never patched in place.

4. Why does maku-backend use strategy: Recreate?

The uploads PVC is RWO. With RollingUpdate, the new pod could land on the other node while the old one still holds the volume, and it would hang in ContainerCreating. The trade-off is a few seconds of downtime per deploy.

5. You run kubectl -n play delete deployment web. What happens to its pods?

Deleting the owner cascades: Deployment → ReplicaSets → Pods (garbage collection via owner references). Try it: kubectl -n play delete deploy web.
Recall: what does the 779d8657fd in maku-backend-779d8657fd-pvnnc mean, and when does it change?

It's the pod-template-hash, identifying one version of the pod template (one ReplicaSet). It changes whenever the template changes: a new image, env, annotation (like our checksum/config), or probes. A new hash means a new ReplicaSet and a rollout.
