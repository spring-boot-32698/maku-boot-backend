Debugging playbook

Eight broken apps. One method. No guessing.

Time ~25 minPrereq lessons 01–10Run from maku-boot-backend/
Your win

Given any unhealthy pod, you know which command reveals the cause, and you've diagnosed eight real failures.

The method: get → describe → logs → events

  1. kubectl get pods: the STATUS and READY columns tell you which phase failed.
  2. kubectl describe pod: read Events at the bottom (scheduling, pulling, probes) and Last State (why the previous container died).
  3. kubectl logs: the app's own words. --previous for a crashed container, -c <name> for an init container.
  4. kubectl get events --sort-by=.lastTimestamp: namespace-wide, including objects that aren't pods (PVCs, ReplicaSets).
  5. Still stuck? Look sideways: the Service's endpoints, the PVC, a debug pod (kubectl run t --rm -it --image=busybox:1.36 -- sh).

Official flow: Debug Pods, Debug Running Pods, Debug Services.

The labs

Eight manifests in .claude/k8s/labs/ (lab-a.yaml … lab-h.yaml), each broken differently. Don't open the files. Diagnose from the cluster only, the way you would at work. You met A and D in lesson 06.

  1. Apply them all and give them a minute to fail.

    kubectl create namespace play
kubectl -n play apply -f .claude/k8s/labs/
sleep 60; kubectl -n play get pods,pvc,svc
    Expected symptoms
    lab-a-…   0/1   Pending
lab-b-…   0/1   ImagePullBackOff
lab-c-…   0/1   Error / CrashLoopBackOff   3 restarts
lab-d-…   0/1   OOMKilled / CrashLoopBackOff
lab-e-…   0/1   Running      (×2)
lab-f-…   1/1   Running      (×2)   ← looks healthy…
lab-g-…   0/1   Init:0/1
lab-h-…   0/1   Pending
persistentvolumeclaim/lab-h-data   Pending   fast-ssd

  2. Lab B. Diagnose, then write the cause in one sentence before opening.

    kubectl -n play describe pod -l app=lab-b | tail -5
    Diagnosis
    Failed to pull image "nginx:1.27-alpinee": … not found

    Typo in the tag. Fix: correct the image. (Other causes of the same symptom: a private registry without imagePullSecrets, or a local image not imported into k3d, as in lesson 09.)

  3. Lab C.

    kubectl -n play logs deploy/lab-c --previous
kubectl -n play describe pod -l app=lab-c | grep -A3 'Last State'
    Diagnosis
    Starting app...
ERROR: required env DB_URL is not set
    Last State:  Terminated   Reason: Error   Exit Code: 1

    The app exits on start because config is missing. Kubernetes restarts it with growing back-off: CrashLoopBackOff. Fix: provide the env (ConfigMap/Secret, lesson 04). This is the most common real-world failure, e.g. a wrong DB password for maku-backend.

  4. Lab E. Pods are Running but never Ready.

    kubectl -n play describe pod -l app=lab-e | grep Unhealthy | tail -1
kubectl -n play get endpointslice -l kubernetes.io/service-name=lab-e \
  -o jsonpath='{range .items[*].endpoints[*]}{.addresses[0]} ready={.conditions.ready}{"\n"}{end}'
    Diagnosis
    Readiness probe failed: HTTP probe failed with statuscode: 404
10.42.0.20 ready=false
10.42.1.17 ready=false

    The probe checks /healthz, which nginx doesn't serve. The Service has endpoints, but none are ready, so it gets no traffic. Fix: probe a real path.

  5. Lab F. Pods are 1/1 and healthy. Test the Service from inside the cluster.

    kubectl -n play run t --rm -it --image=busybox:1.36 --restart=Never -- wget -qO- -T 3 http://shop
kubectl -n play get endpointslices -l kubernetes.io/service-name=shop
kubectl -n play get svc shop -o jsonpath='{.spec.selector}'; echo
kubectl -n play get pods --show-labels | grep lab-f
    Diagnosis
    wget: can't connect to remote host (10.43.170.103): Connection refused
shop-…   IPv4   <unset>   <unset>      ← no endpoints at all
{"app":"shopp"}                       ← selector typo
lab-f-…  app=shop

    The selector matches nothing. Nothing in the pods is wrong, which is why get pods can't find this bug. Note the instant “Connection refused”: kube-proxy actively rejects traffic to a Service with no endpoints. A timeout instead points elsewhere (NetworkPolicy, a pod not listening).

  6. Lab G.

    kubectl -n play logs deploy/lab-g -c wait-for-db --tail=3
    Diagnosis
    nc: bad address 'orders-db'
waiting for orders-db

    The init container waits for a Service that doesn't exist (wrong name or wrong namespace). Remember from lesson 03 that a cross-namespace name would need orders-db.<namespace>. Same shape as maku's wait-for-mysql.

  7. Lab H. Pending, but not for CPU.

    kubectl -n play describe pod -l app=lab-h | tail -2
kubectl -n play describe pvc lab-h-data | tail -2
kubectl get storageclass
    Diagnosis
    0/2 nodes are available: pod has unbound immediate PersistentVolumeClaims …
ProvisioningFailed   storageclass.storage.k8s.io "fast-ssd" not found

    The PVC asks for a StorageClass this cluster doesn't have (it exists only on some other platform). Fix: use an existing class, or omit it for the default (local-path). This is common when a chart from a cloud cluster meets a local one.

  8. Namespace-wide view, then clean up.

    kubectl -n play get events --sort-by=.lastTimestamp | tail -15
kubectl delete namespace play

Practice: match symptom to cause

1. A pod is CrashLoopBackOff. The current container just restarted and its logs are empty. Next command?

--previous shows the output of the container instance that crashed. That's where the stack trace is.

2. A pod is Pending; Events say “pod has unbound immediate PersistentVolumeClaims”. What do you check?

The scheduler is waiting for storage. describe pvc told us the class doesn't exist (lab H).

3. All pods are 1/1 Running, yet connections to the Service are refused instantly. First suspect?

Healthy pods plus a dead Service point to wiring. get endpointslices → empty → compare svc .spec.selector with --show-labels (lab F).

4. maku-backend is Running 0/1 right after a MySQL restart, with no restarts counting up. Most likely?

Our readiness group includes db. No restarts means liveness is fine. It should recover by itself; if it doesn't, check the backend logs for connection-pool errors.

5. Where do you find why a container was killed with exit code 137?

137 = SIGKILL. Reason: OOMKilled means memory limit; otherwise it may be a liveness kill (then Events say “Liveness probe failed … will be restarted”). The app usually logs nothing; it was killed mid-flight.
Recall (interview): “A pod is in CrashLoopBackOff. Walk me through debugging it.”

CrashLoopBackOff means the container starts and exits repeatedly, and Kubernetes backs off between restarts. 1) kubectl describe pod: Last State (exit code, OOMKilled?), Events (liveness kills?). 2) kubectl logs --previous: the crash output. 3) Common causes: missing or wrong config/secrets, a dependency unreachable at boot, bad command/args, OOM (exit 137), a liveness probe too aggressive for a slow start (use a startup probe). 4) Reproduce interactively: override the command with sleep and exec in, or use kubectl debug.
