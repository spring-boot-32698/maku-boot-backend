Services and DNS

Pods come and go with new IPs. A Service is the address that stays put.

Time ~15 minPrereq Lesson 02Namespaces maku, play
Your win

You can explain how jdbc:mysql://maku-mysql:3306 reaches the MySQL pod, and debug a Service with no endpoints.

The problem

In lesson 01 you saw a deleted pod come back with a new name. It also gets a new IP. If the backend connected to MySQL's pod IP, every MySQL restart would break it. Compose solved this with service-name DNS on its network; Kubernetes solves it with a Service.

How a Service works

Service maku-mysql   ClusterIP 10.43.200.245:3306   selector: component=mysql, instance=maku
        │  (kube-proxy routes the virtual IP to…)
        ▼
EndpointSlice        10.42.0.11:3306 ready=true   ← pods matching the selector, updated live
        ▼
Pod maku-mysql-0     10.42.0.11
  • Selector: same label mechanism as ReplicaSets. The Service never names pods.
  • EndpointSlice: lists the pods matching the selector, each with a ready condition. Traffic goes only to ready ones, so a failing readiness probe removes a pod from traffic without killing it (lesson 06).
  • DNS: CoreDNS gives every Service the name <service>.<namespace>.svc.cluster.local. Inside the same namespace the short name maku-mysql works, thanks to the pod's DNS search list.
  • port / targetPort: maku-backend listens on port: 8080 and forwards to the container port named http.

Hands-on

  1. List maku's Services. Note CLUSTER-IP; the headless one has None.

    kubectl -n maku get svc

  2. Match a Service to its pod: the endpoint IP should equal the pod IP.

    kubectl -n maku get endpointslices -l kubernetes.io/service-name=maku-backend
kubectl -n maku get pods -l app.kubernetes.io/component=backend -o wide

  3. Ask cluster DNS from a throwaway pod. Watch the resolver try the search domains before finding the full name.

    kubectl -n maku run dns-test --rm -it --image=busybox:1.36 --restart=Never -- \
  sh -c 'cat /etc/resolv.conf; nslookup maku-mysql; nslookup maku-mysql-headless'
    Expected output (trimmed)
    search maku.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.43.0.10                         ← CoreDNS's own Service IP
options ndots:5
** server can't find maku-mysql.svc.cluster.local: NXDOMAIN   ← search list being tried
Name:    maku-mysql.maku.svc.cluster.local
Address: 10.43.200.245                         ← the ClusterIP (virtual)
Name:    maku-mysql-headless.maku.svc.cluster.local
Address: 10.42.0.11                            ← the POD's IP (headless)

  4. See where the backend gets the name from.

    kubectl -n maku get configmap maku-backend -o yaml | grep -E 'URL|HOST'
    Expected output
    SPRING_DATASOURCE_DYNAMIC_DATASOURCE_MASTER_URL: jdbc:mysql://maku-mysql:3306/maku_boot?…
SPRING_DATA_REDIS_HOST: maku-redis

  5. Reach a ClusterIP Service from your laptop with a tunnel (debugging only). Leave it running, then use a second terminal.

    kubectl -n maku port-forward svc/maku-backend 18080:8080
    curl -s localhost:18080/actuator/health
    Expected output
    {"groups":["liveness","readiness"],"status":"UP"}

  6. Break it on purpose in play: expose your web Deployment (recreate it if you deleted it in lesson 02), then scale it to zero.

    kubectl -n play create deployment web --image=nginx:1.27-alpine --replicas=2   # if needed
kubectl -n play expose deployment web --port=80
kubectl -n play get endpointslices -l kubernetes.io/service-name=web
kubectl -n play scale deploy/web --replicas=0
kubectl -n play get endpointslices -l kubernetes.io/service-name=web
    What to notice

    Endpoints go from two IPs to <unset>. The Service still exists and its DNS name still resolves, but connections fail: nothing is behind it. That's the #1 “my Service doesn't work” cause: no ready pods match the selector.

Earlier, when we deleted maku's backend pod, the ingress returned 404 page not found for about 3 s until the new pod became ready and its IP reached the EndpointSlice. That gap is exactly what readiness and endpoint propagation look like.

Practice

1. Why does the backend connect to maku-mysql instead of the MySQL pod's IP?

Pods are replaced with new IPs; the Service's name and ClusterIP stay fixed while its endpoints follow the pods.

2. A pod in namespace play needs maku's MySQL. Which hostname works?

The format is service.namespace (full: maku-mysql.maku.svc.cluster.local). The short name maku-mysql only resolves inside namespace maku, because the search list starts with your own namespace.

3. A Service exists but has no endpoints. Most likely cause?

No endpoints at all means the selector matches no pods: check labels (--show-labels) and replicas > 0. (Endpoints that exist but show ready=false mean the pods are failing readiness; lesson 11, lab E.)

4. maku-backend's Service has port: 8080, targetPort: http. What does that mean?

targetPort can be a name: the Deployment declares containerPort: 8080, name: http. Naming ports lets you change numbers in one place.

5. All of maku's Services are ClusterIP. Why is that enough for browser traffic?

Traefik (itself behind a LoadBalancer Service that k3d maps to :8088) receives requests and forwards them to our ClusterIP Services by host name. Lesson 07 goes deeper.
Recall (interview): “Explain the four Service types and when you'd use each.”

ClusterIP: internal service-to-service (default; DBs, APIs behind an ingress). NodePort: quick external access on every node's IP at a high port (demos, bare metal behind your own LB). LoadBalancer: cloud provider gives an external IP/LB (exposing an ingress controller or a TCP service). Headless: no virtual IP; DNS returns pod IPs, used with StatefulSets so clients can address specific pods (maku-mysql-0.maku-mysql-headless).
