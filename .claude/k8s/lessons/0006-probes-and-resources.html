Probes and resources

Kubernetes can only keep your app healthy if it can tell when it isn't, and how much it needs.

Time ~15 minPrereq Lesson 05Run from maku-boot-backend/
Your win

You can explain which probe should fail when a dependency is down, read an OOMKilled pod, and say why a pod is stuck Pending on resources.

Three probes, three different consequences

ProbeQuestionWhen it failsmaku-backend
startupHas it finished booting?Keeps waiting; the other probes are paused until it succeeds. If it never succeeds → restart./actuator/health/liveness, every 5 s, up to 60 tries (5 min) for Liquibase + JVM start
readinessShould it receive traffic right now?Pod marked 0/1, its endpoint becomes ready=false. No restart./actuator/health/readiness, includes db and redis
livenessIs it stuck beyond repair?The kubelet kills and restarts the container./actuator/health/liveness, the app's own state only

Sources: Liveness, Readiness and Startup Probes (concepts) and how to configure them. Spring's side: Actuator endpoints; we configured groups in application.yml → management.endpoint.health.group.readiness.

The design rule: put dependencies (DB, Redis) in readiness, never in liveness. If Redis is down, restarting every backend pod can't fix Redis. It just turns one outage into a restart storm.

Each probe also has timeoutSeconds, which defaults to 1 second. When I tested this lesson, the readiness check timed out (“context deadline exceeded”) while Redis was down, and a long JVM garbage-collection pause could do the same to liveness. The chart now sets 3 s (backend.probes.*.timeoutSeconds).

Requests and limits

resources:
  requests: { cpu: 250m, memory: 768Mi }   # scheduler RESERVES this on a node; pods only land where it fits
  limits:   { memory: 1536Mi }             # hard ceiling: exceed memory → container OOMKilled (exit 137)
  • Requests drive scheduling. A pod whose requests fit on no node stays Pending.
  • Memory limit is enforced by killing the container. CPU limit is enforced by throttling (it slows down, but isn't killed). Many teams set no CPU limit for latency-sensitive apps; we don't set one.
  • JVM trap: the image starts Java with -Xmx1024M. Heap isn't everything (metaspace, threads, buffers), so the limit must leave headroom: 1536Mi. kubectl top showed the backend using ~640Mi at rest.

250m = 0.25 CPU (milli-cores). Mi = mebibytes. See Resource management for pods and Assign memory resources.

Practice

1. Redis goes down. Which backend probe should fail?

You saw it: 0/1 Running, 0 restarts, Traefik stopped routing to it. When Redis came back, readiness passed and traffic resumed with no restart needed.

2. Why keep DB and Redis checks out of the liveness probe?

A shared dependency failing would make every replica fail liveness and restart together, piling slow JVM boots onto an incident. Liveness answers only “is this process wedged?”.

3. A pod shows OOMKilled, exit code 137. What happened?

The kernel's OOM killer sends SIGKILL (9) when the cgroup memory limit is hit: exit 128+9 = 137. CPU over limit is throttled, never killed. A Java OutOfMemoryError is a different thing: the JVM ran out of heap within its -Xmx.

4. Lab A stays Pending with “2 Insufficient cpu”. What did the scheduler compare?

Scheduling is bookkeeping on requests, not live usage. Requests too high wastes capacity; too low and nodes get overcommitted.

5. Why does the backend have a startup probe allowing 5 minutes?

Without it, liveness (3 × 20 s) could kill a JVM still running Liquibase on first install, over and over. The startup probe pauses liveness and readiness until the app is up, then gets out of the way.
Recall (interview): “Readiness vs liveness: what's the difference, and give an example of getting it wrong.”

Readiness gates traffic (fail = removed from Service endpoints, no restart). Liveness gates life (fail = container restarted). Getting it wrong: putting a database check in liveness, so a DB blip restarts every pod at once; or having no readiness probe, so traffic hits a JVM that's still booting and users see errors during every deploy.
