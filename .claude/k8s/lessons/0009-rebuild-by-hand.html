Rebuild maku by hand

Delete everything. Then bring it back yourself, no script, reading every status on the way.

Time ~25 minPrereq lessons 01–08Run from maku-boot-backend/
Your win

maku running on a cluster you created from nothing, and you can explain every status each pod passed through.

This lesson is the milestone from your mission: “bring maku up from zero, step by step”. It deliberately includes one classic mistake (installing before the images are in the cluster) so you can watch Kubernetes recover from it.

This deletes dataDeleting the cluster deletes its volumes: users you created, uploaded files, everything. Liquibase recreates the schema and demo accounts on the next start. Your Docker images stay.

The plan

  1. k3dDelete and recreate the cluster
  2. helmInstall the chart (too early, on purpose)
  3. k3dLoad the images and watch the pods recover
  4. verifyWatch the backend boot, then test it all

Hands-on

  1. Tear down. Nodes are containers, so watch them disappear.

    k3d cluster delete maku
docker ps --filter name=k3d-maku
kubectl config get-contexts
    What to notice

    No containers, and the k3d-maku context is gone. kubectl may now point at k3d-ecommerce or nothing. That's exactly why you always check the context first.

  2. Create the cluster from its config file and confirm it's yours.

    cat deploy/k3d/cluster.yaml
k3d cluster create --config deploy/k3d/cluster.yaml
kubectl config current-context
kubectl get nodes
kubectl get pods -n kube-system
    Expected output
    k3d-maku
NAME                STATUS   ROLES                  VERSION
k3d-maku-agent-0    Ready    <none>                 v1.31.5+k3s1
k3d-maku-server-0   Ready    control-plane,master   v1.31.5+k3s1

    Wait until traefik is Running in kube-system (about a minute) before relying on the ingress.

  3. Your images still exist in Docker. Check them; rebuild only if missing (the UI must be built with the cluster's API URL).

    docker images | grep -E '^maku-(boot|admin) '
# only if missing:
# docker build -t maku-boot:5.0.0 .
# docker build -t maku-admin:5.0.0 --build-arg VITE_API_URL=http://api.maku.localhost:8088 ../maku-admin-frontend

  4. Predict, then install too early. The images are in Docker, but have we told the cluster about them? Open a watcher first: kubectl -n maku get pods -w (re-run once the namespace exists).

    helm upgrade --install maku deploy/helm/maku -n maku --create-namespace -f deploy/helm/maku/values-k3d.yaml
kubectl -n maku get pods
    What you'll see
    maku-mysql-0                0/1   Running            ← pulled mysql:8.0 from Docker Hub
maku-redis-…                1/1   Running            ← pulled redis:7-alpine from Docker Hub
maku-frontend-…             0/1   ImagePullBackOff   ← maku-admin:5.0.0 isn't on any registry
maku-backend-…              0/1   Init:0/1           ← init container waiting for MySQL…
                                                       …then ErrImagePull / ImagePullBackOff

    kubectl -n maku describe pod -l app.kubernetes.io/component=frontend | tail -3 shows Failed to pull image "maku-admin:5.0.0" … docker.io/library/maku-admin:5.0.0 … not found. The cluster's nodes run their own containerd; your laptop's Docker image store is invisible to them.

  5. Fix it by copying the images into every node, then watch the pods recover by themselves. The kubelet retries pulls with growing back-off; when I tested this it recovered about 10 s after the import. If one seems stuck, deleting the pod skips the wait.

    k3d image import maku-boot:5.0.0 maku-admin:5.0.0 -c maku
kubectl -n maku get pods -w

  6. Follow the backend's boot sequence. Each status means something:

    kubectl -n maku logs deploy/maku-backend -c wait-for-mysql
kubectl -n maku logs deploy/maku-backend -c backend -f | grep -E 'liquibase.*(Running|Run:)|Started ServerApplication'
    The sequence
    Init:0/1         wait-for-mysql loops "waiting for mysql" until port 3306 answers
PodInitializing  init finished, main container starting
Running 0/1      JVM up, Liquibase applying changesets; startup probe not yet passing
Running 1/1      startup passed → readiness passed (db + redis UP) → endpoint ready
logs: Running Changeset: …0001-baseline-core … Run: 6 … Started ServerApplication in ~15 s

  7. Verify like you would at work: release status, smoke test, real requests, real login.

    helm list -n maku
helm test maku -n maku
curl -s http://api.maku.localhost:8088/actuator/health; echo

    Open http://maku.localhost:8088 and log in as admin/admin. helm history maku -n maku starts again at revision 1, because the release history lived in the old cluster (as Secrets in the namespace).

Practice

1. maku-admin:5.0.0 exists in docker images, yet the pod shows ImagePullBackOff. Why?

Each node's containerd only sees images pulled from a registry or imported into it. k3d image import copies them in; real clusters pull from a registry (lesson 12).

2. Why did MySQL and Redis start fine at the same moment?

An unqualified image name like mysql:8.0 means docker.io/library/mysql:8.0. The cache died with the old cluster; they were pulled fresh.

3. The backend sits at Init:0/1. What is it doing?

Init:0/1 = zero of one init containers completed. Ours loops on nc -z maku-mysql 3306; its logs are under -c wait-for-mysql. Liquibase runs later, during Running 0/1.

4. Why is it Running 0/1 for a while before 1/1?

READY counts containers passing readiness. Until startup and then readiness succeed, the endpoint is ready=false and the ingress won't route to it.

5. In step 4 we ran helm upgrade --install without --wait. With --wait and a 5-minute timeout, what would Helm have done?

--wait blocks until resources are ready. Pods stuck in ImagePullBackOff never are, so you'd get a failed revision (without --rollback-on-failure, nothing is undone, and there was no previous revision anyway).
Recall: list every command, in order, to go from no cluster to a working maku. Write them down, then open. 
k3d cluster create --config deploy/k3d/cluster.yaml
kubectl config current-context
docker build -t maku-boot:5.0.0 .
docker build -t maku-admin:5.0.0 --build-arg VITE_API_URL=http://api.maku.localhost:8088 ../maku-admin-frontend
k3d image import maku-boot:5.0.0 maku-admin:5.0.0 -c maku
helm upgrade --install maku deploy/helm/maku -n maku --create-namespace -f deploy/helm/maku/values-k3d.yaml --wait --timeout 10m
helm test maku -n maku

That's deploy/k3d/up.sh. You can now read every line of it and know why it's there.
