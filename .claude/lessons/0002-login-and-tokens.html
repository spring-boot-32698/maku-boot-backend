Login, tokens and refresh

The token here is not a JWT. That one fact explains most of the design.

Time ~10 minPrereq Lesson 01Deep dive docs/03 §1–2
Your win

You can explain what happens on login, on every request, and when the token expires — and find a logged-in user's session in Redis.

The token is a key, not a passport

On login the server generates two random UUIDs — an access token and a refresh token. The access token is just a Redis key:

sys:token:<accessToken>  →  UserDetail { id, username, orgId, superAdmin,
                                         authoritySet: ["sys:user:save", "ROLE_hr", …],
                                         dataScopeList: [2, 3] }        TTL 8 h

On every request AuthenticationTokenFilter reads the Authorization header (raw token, no “Bearer”), fetches that key, and puts the UserDetail into Spring's SecurityContextHolder. No key → the request is anonymous → protected URLs get {"code":401}.

Spring Security's Servlet Architecture page explains filters and SecurityContextHolder. Files: maku-framework/…/security/filter/AuthenticationTokenFilter.java, …/cache/TokenStoreCache.java.

Why not JWT? Because the server owns the session, it can revoke it (logout, “kick user” in Monitor) and rewrite the user's permissions while they're logged in — something a signed JWT can't do.

Login, step by step

  1. FEaccount.vue SM2-encrypts the password with a public key in src/utils/smCrypto.ts.
  2. BEPOST /sys/auth/login → captcha check (off by default: param LOGIN_CAPTCHA=false).
  3. BEAuthenticationManager → DaoAuthenticationProvider loads the user, computes authorities + data scope, compares SM3 hashes.
  4. BEcreateToken() upserts sys_user_token (one row per user); saveUser() writes Redis.
  5. FEStores access_token/refresh_token in localStorage (maToken, maRefreshToken), then the router guard loads user info, permissions, dictionaries and menus.

The AuthenticationManager is a ProviderManager with three providers — password, SMS code, third-party — see Authentication Architecture and maku-boot-system/…/security/config/SecurityConfig.java.

Expiry: the silent refresh

TokenLivesStored
access8 h (maku.security.access-token-expire)Redis + sys_user_token
refresh14 dayssys_user_token only

When the Redis key expires, the next call returns code 401. src/utils/request.ts then calls POST /sys/auth/token?refreshToken=…, gets a new access token (the backend reloads permissions from the DB while doing so), and replays the failed request plus any that queued up meanwhile. If the refresh token is also dead the backend answers code 400 and the UI shows “Login timed out”.

Axios interceptors are what make this invisible to page code.

Live permission updates

When an admin edits a role or user, SysUserTokenServiceImpl.updateCacheAuthByRoleId/UserId finds that user's still-valid access tokens in sys_user_token and rebuilds each cached UserDetail, keeping its TTL. The backend enforces the change at once; the browser only shows new menus/buttons after a reload.

Practice

Answer from memory first.

1. On each authenticated request, where does the backend find out who you are?

TokenStoreCache.getUser(accessToken) reads sys:token:<token>. Sessions are STATELESS in SecurityFilterConfig, and the token is a random UUID, not a JWT.

2. A user's access token expired an hour ago; their refresh token is still valid. They click “Save”. What do they see?

The code 401 is caught by the axios response interceptor, which refreshes the token and replays the request. The user never notices.

3. The refresh token has expired too (15 days idle). What does POST /sys/auth/token return?

refreshToken() throws ServerException(ErrorCode.REFRESH_TOKEN_INVALID) = 400. request.ts maps 400 to handleAuthorized() → “Login timed out” → back to /login.

4. An admin removes a permission from role R. User U (role R) is logged in right now. When does the backend start rejecting U?

SysRoleServiceImpl.update calls updateCacheAuthByRoleId, which rewrites each online user's cached authorities. (U's browser keeps showing the button until a reload — but clicking it now returns 403.)

5. Why does curl -d '{"username":"admin","password":"admin"}' …/sys/auth/login fail?

The server calls Sm2Util.decrypt(login.getPassword()) before authenticating. SM3 is how the password is stored, hashed server-side. Captcha is off by default.
Recall: name the two places a valid access token is recorded, and which one the request filter actually reads.

Redis (sys:token:<token> → UserDetail) and the sys_user_token table. The filter reads only Redis; the table is used for refresh, logout and finding a user's online tokens.

Try it

Log in via the UI, then run redis-cli -n 1 --scan --pattern 'sys:token:*' (dev Redis uses database 1). Copy your token from DevTools → Local Storage → maToken and call curl -H "Authorization: $TOKEN" localhost:8080/sys/user/info. Then delete the key and watch the UI refresh it on the next click (Network tab).
