Data scope: who sees which rows

Permissions decide what you can do. Data scope decides which rows you see while doing it.

Time ~10 minPrereq Lesson 03Deep dive docs/03 §4
Your win

Given a user's org and roles, you can write down the exact SQL filter they get — and opt a new query into it.

Five levels, set per role

ValueDataScopeEnumRows visible
0ALLeverything — no filter
1ORG_AND_CHILDmy org + all its descendants (+ custom orgs) + rows I created
2ORG_ONLYmy org (+ custom orgs) + rows I created
3SELFonly rows I created
4CUSTOMorgs ticked in sys_role_data_scope + rows I created

New roles start as SELF (SysRoleServiceImpl.save). Change it with PUT /sys/role/data-scope.

Several roles? SysRoleDao.getDataScopeByUserId runs select min(data_scope). Lower number = broader, so the broadest role wins.

From scope to SQL

At login (and refresh), SysUserDetailsServiceImpl.getDataScope turns the scope into UserDetail.dataScopeList: null means “all”; otherwise a list of org IDs (empty for SELF). Later, BaseServiceImpl.getDataScope(alias, orgColumn) turns that list into a SQL fragment:

-- dataScopeList = [3, 2], user id = 42
 (org_id in(3,2) or creator=42)
-- dataScopeList = []  (SELF)
 (creator=42)
-- dataScopeList = null (ALL) or super admin
 (no filter at all)

Opting in — it is not automatic

A query is only filtered if the service asks for it. Two ways:

// 1) Lambda wrapper (simple single-table queries)
LambdaQueryWrapper<ProductEntity> w = new LambdaQueryWrapper<>();
dataScopeWrapper(w);                                  // appends the fragment via w.apply(...)

// 2) XML query (joins) — pass a DataScope object as a mapper parameter
params.put(Constant.DATA_SCOPE, getDataScope("t1", "id"));
baseMapper.getList(params);   // DataScopeInnerInterceptor parses the SQL with JSqlParser
                              // and ANDs the fragment into the WHERE clause

Interceptor: maku-framework/…/mybatis/interceptor/DataScopeInnerInterceptor.java, registered first in MybatisPlusConfig. MyBatis-Plus plugin docs explain InnerInterceptor.

Today only the role list and the org tree opt in. The user list has the line commented out in SysUserServiceImpl#getParams. For your own tables, include org_id (auto-filled on insert) and creator so the fragment has columns to hit.

Practice

Org tree for all questions: HQ (1) → Sales (2) → Sales-North (3); and HQ (1) → Ops (4). Ana (user id 42) belongs to Sales (2).

1. Ana's only role is ORG_AND_CHILD, no custom orgs. Which org IDs appear in her filter?

getSubOrgIdList(2) walks down the tree (3) and then adds Sales itself (2). Parents (HQ) are never included.

2. Ana gets a second role: she now has SELF (3) and ORG_ONLY (2). Effective scope?

select min(t1.data_scope) → 2 = ORG_ONLY → filter (org_id in(2) or creator=42).

3. You write a new list query with LambdaQueryWrapper. What makes it respect data scope?

The interceptor only acts when a DataScope object is among the mapper parameters. With wrappers, dataScopeWrapper applies the fragment directly. There's no @DataScope annotation in this codebase.

4. Ana's role is ALL. Her colleague Ben is a super admin with no roles. Who sees more rows on the role list?

getDataScope returns null for super admins first, and for a null dataScopeList (= ALL). No fragment, no filter.
Recall: a user has no roles at all and is not super admin. What do they see on a data-scoped list?

getDataScopeByUserId returns null → getDataScope returns an empty list → fragment (creator=<id>). Same as SELF: only their own rows.

Try it

Create orgs HQ → Sales → Sales-North, a role per scope, and a user in Sales. Log in as them and open Org Management while switching the role's scope. Turn on MyBatis SQL logging (logging.level.net.maku=debug) to watch the rewritten WHERE clause.
