Permissions: menus, buttons, codes

One string — a permission code — has to match in three places.

Time ~10 minPrereq Lesson 02Deep dive docs/03 §3
Your win

You can make a button appear for exactly the right roles and be enforced on the server — and diagnose it when it isn't.

The model

sys_user ─< sys_user_role >─ sys_role ─< sys_role_menu >─ sys_menu
                                                          type 0 = menu    (url → Vue page)
                                                          type 1 = button  (authority = codes)

A permission code looks like sys:post:save (module:resource:action). A button row's authority column may hold several, comma-separated: sys:menu:update,sys:menu:info.

The same code, three places

WhereLooks likeRole
BE Controller@PreAuthorize("hasAuthority('sys:post:save')")The real gate. Missing code → {"code":403}
DB sys_menu.authoritysys:post:save on a type-1 rowWhat a role is granted (via sys_role_menu)
FE Templatev-auth="'sys:post:save'"Cosmetic: removes the element from the DOM

@PreAuthorize works because of @EnableMethodSecurity on SecurityFilterConfig — see Method Security. The directive is src/utils/directive/auth.ts.

At login, SysMenuServiceImpl.getUserAuthority collects every code from the user's roles' menus, splits on commas, and adds ROLE_<roleCode> for each role. That set becomes UserDetail.authoritySet in Redis. The UI gets the same list from GET /sys/menu/authority.

Two special cases

Super admin (sys_user.super_admin = 1, e.g. admin): instead of reading menus, PreAuthorizeUtil scans every controller for hasAuthority('…') and grants them all. New endpoints “just work” for admin — which is why testing only as admin hides permission bugs.

No @PreAuthorize: the endpoint only requires a valid login. Examples: GET /sys/post/page, GET /sys/user/page.

Watch outThe browser caches the menu tree and authority list until a full reload. After changing a role, the backend enforces it immediately (lesson 02), but the user won't see new menus until they refresh.

Practice

1. User U sees the “Add” button, but clicking it returns {"code":403}. Most likely cause?

The button is visible, so U has the code used in v-auth; the server checks a different one. An expired token gives 401, not 403. Data scope filters rows, never returns 403.

2. Which user automatically has every permission code, with no menu rows needed?

getUserAuthority branches on SuperAdminEnum.YES and returns PreAuthorizeUtil.getPreAuthorizeList(). Role names and data scope don't grant codes.

3. A type-1 sys_menu row named “Modify” has authority = "sys:menu:update,sys:menu:info". What does granting it give?

Codes are split on commas into the authority set. “Modify” needs info too, because the edit dialog first loads the record via GET /sys/menu/{id} (sys:menu:info).

4. A controller method has no @PreAuthorize and its URL is not in any auth.yml. Who can call it?

SecurityFilterConfig: anyRequest().authenticated(). Only the method annotation narrows it further; only auth.yml opens it up.

5. You granted a new menu to role R. A logged-in user with R doesn't see it in the sidebar. What fixes it?

Menus come from GET /sys/menu/nav, called once by the router guard when user.id is empty — i.e. after a reload.
Recall: list the three places the code biz:product:delete must appear for a non-admin to delete a product from the UI.

(1) @PreAuthorize("hasAuthority('biz:product:delete')") on the controller; (2) a type-1 sys_menu row with that authority, granted to the user's role; (3) v-auth="'biz:product:delete'" on the button (optional for security, needed for UX).

Try it

As admin: create role “Viewer” with only Post Management → Query, create a user with that role, log in as them in a private window. The Add/Edit/Delete buttons should vanish. Then call POST /sys/post with their token via curl and confirm {"code":403}.
